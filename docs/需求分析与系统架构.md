# 智选 · 无人零售导购 Agent 与多模态结账系统
## 需求分析与系统架构设计

> 版本：v1.0 ｜ 日期：2026-08-30 ｜ 状态：方案评审稿

---

## 一、需求分析

### 1.1 干系人与核心诉求

| 角色 | 核心诉求 | 关键痛点 |
|---|---|---|
| 消费者 | 找得到、问得清、付得快 | 无人店无人可问；逐件扫码排队累；看不懂配料表与促销 |
| 门店运营方 | 少人值守、损耗可控、坪效提升 | 人力成本高；盘点难；促销触达弱 |
| 平台/技术方 | 识别准、可追溯、可复制 | 相似商品误判；争议无凭证；单店定制成本高 |

### 1.2 用户旅程与系统能力映射

进店（身份识别） → 导购咨询（自然语言问答） → 取货（货架定位） → 视觉结账（多目标识别） → 支付离店（极速支付）

- 导购阶段决定**体验上限**
- 结账阶段决定**效率与信任下限**

### 1.3 需求拆解

#### 明确需求（Must）

1. 自然语言咨询：商品位置、营养成分、促销搭配
2. 视觉结账：摄像头拍摄购物盘 → 多目标识别 → 品名匹配 → 价格计算 → 生成账单 → 引导支付

#### 隐含需求（工程上不可缺失）

| 隐含需求 | 必要性 | 说明 |
|---|---|---|
| 商品主数据与库存一致性 | 必需 | 识别结果需映射到 SKU + 实时价格，否则"识别对了但算错钱" |
| 置信度分级与人工兜底 | 必需 | 视觉不可能 100% 准确，低置信必须转追问/复核，不能硬出账 |
| 重量 / 重力校验 | 必需 | 解决漏检、遮挡、作弊；摄像头看不见被压住的商品 |
| 争议留痕与账单可追溯 | 必需 | 无人店无店员，投诉必须有证据链 |
| 支付对账与退款 | 必需 | 资金流闭环 |
| 促销规则引擎 | 必需 | "促销搭配"要能真实计算金额 |
| 隐私合规 | 必需 | 店内摄像涉及个人信息，需边缘处理 + 脱敏 + 告知 + 留存期限 |
| 离线降级 | 建议 | 断网不能堵住结算，边缘缓存商品库 + 本地识别 + 事后补账 |

### 1.4 非功能性指标（建议值）

| 指标 | 目标 |
|---|---|
| 视觉识别 Top-1 准确率 | ≥ 98%（标品 SKU 池 ≤ 2000） |
| 单盘结算端到端耗时 | ≤ 3s |
| 导购问答首字延迟 | ≤ 800ms，答案须带商品来源 |
| 结算链路可用性 | 99.9%，断网可离线降级 |
| 漏检率 | ≤ 0.5%（视觉 + 重量双校验后） |

## 二、功能模块清单

### A. 智能导购 Agent（LLM + RAG + 工具调用）

- 商品位置问答（货架 / 层数 / 导航）
- 营养成分与配料问答
- 促销与搭配推荐
- 禁忌与过敏提示
- 多轮上下文与追问澄清
- 语音输入 / 输出

### B. 视觉结账（多模态）

- 多角度拍摄引导（顶视 + 侧视）
- 目标检测与实例分割
- 细粒度特征匹配（相似品区分）
- 数量统计
- 重量校验
- 置信度分级与人工复核
- 账单生成与可视化确认

### C. 交易与支付

- 订单聚合、促销 / 会员价计算
- 微信 / 支付宝 / 刷脸支付
- 退款与对账

### D. 门店运营后台

- 商品与 SKU 管理、货架位管理
- 视觉样本标注与模型迭代
- 复核工单处理
- 销售与损耗分析

## 三、系统架构

### 3.1 架构原则

**端—边—云协同 + 服务化分层**

- 视觉推理放**边缘**：低延迟 + 隐私不出店
- LLM 导购放**云端**：模型大、迭代快
- 商品 / 价格 / 交易在**数据层强一致**

### 3.2 分层架构

| 层 | 组成 |
|---|---|
| 终端层 | 手机小程序、店内导购屏、结算台终端、边缘摄像头（+称重） |
| 接入层 | API 网关、实时消息推送、鉴权与限流、设备接入 |
| 业务层 | 导购服务、结账服务、商品中心、交易支付 |
| AI 能力层 | 大模型网关、知识库检索（RAG）、视觉推理、决策仲裁 |
| 数据层 | PostgreSQL、Redis + MQ、向量库、对象存储 |

### 3.3 视觉结账核心链路

```
多角度拍摄（顶视+侧视+称重）
   ↓
检测与分割（定位每个商品个体）
   ↓
细粒度匹配（区分相似包装）
   ↓
置信度判定（视觉分 + 重量差 + 规则仲裁）
   ├─ 高置信 → 自动入账
   └─ 低置信 → 主动追问 / 人工复核工单
   ↓
生成账单（促销 + 会员价计算）
   ↓
极速支付（扫码 / 刷脸）→ 离店
```

关键设计：**不做"一锤子买卖"的端到端识别**，而是「检测 → 匹配 → 仲裁 → 兜底」的分级流水线，把不可控的视觉误差转化为可控的工程问题。

## 四、代码工程架构

### 4.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue3 + TypeScript + Vite + Pinia；小程序用 Taro / 原生 | 一套 TS 类型复用；结算台为大屏 Web |
| 后端 | Python 3.11 + FastAPI + SQLAlchemy 2.0 + Pydantic v2 + Celery | 视觉 / LLM / RAG 生态全在 Python |
| 存储 | PostgreSQL 16、Redis 7、Milvus / pgvector、MinIO、RabbitMQ | 订单强一致 + 向量检索 + 图像审计 |
| 视觉 | YOLOv11 / RT-DETR（检测）+ SAM2（分割）+ DINOv2 / CLIP（特征）+ Qwen-VL（兜底） | 检测保证快，特征检索保证相似品可分 |
| LLM | Qwen3 / DeepSeek-V3，经 LiteLLM 统一网关 | 可替换、控成本、便于私有化 |
| 边缘 | Jetson Orin / RK3588 + TensorRT | 结算 ≤ 3s 必须本地推理 |
| 支付 | 微信支付 / 支付宝（扫码 + 刷脸） | 保留支付抽象层 |

### 4.2 工程目录（Monorepo）

```
supermarket/
├── apps/
│   ├── miniapp/            # 小程序：导购问答、账单确认、支付
│   ├── kiosk-web/          # 结算台终端（Vue3）
│   ├── guide-screen/       # 店内导购大屏
│   └── admin-web/          # 运营后台：商品、标注、复核、报表
├── services/
│   ├── gateway/            # 鉴权、限流、路由、设备接入
│   ├── shopping-agent/     # 导购 Agent：RAG + 工具调用 + 多轮
│   ├── checkout/           # 结账编排（核心状态机）
│   ├── catalog/            # 商品/SKU/价格/库存/促销
│   ├── trade/              # 订单、支付、退款、对账
│   └── review/             # 低置信人工复核工单
├── ai/
│   ├── vision-detect/      # 检测+分割服务（Triton / TorchServe）
│   ├── vision-embed/       # 细粒度特征与向量检索
│   ├── vlm-fallback/       # 多模态兜底与主动追问
│   └── rag/                # 商品知识库：切片、向量化、检索
├── edge/
│   ├── capture-agent/      # 多相机采集、称重、图像预处理
│   └── offline-cache/      # 断网降级与事后补账
├── packages/
│   ├── proto/              # OpenAPI / Protobuf 契约（唯一真源）
│   └── shared/             # 前端共享组件与 TS 类型
├── infra/                  # docker-compose、k8s、SQL migrations
└── tests/                  # 契约测试 / 识别准确率回归集
```

### 4.3 核心接口契约

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v1/agent/ask` | POST (SSE) | 导购问答，流式返回，答案携带商品引用 |
| `/api/v1/checkout/sessions` | POST | 创建结账会话（绑定设备 / 用户 / 购物盘） |
| `/api/v1/checkout/sessions/{id}/frames` | POST | 上传图像帧 + 重量，返回识别候选项 |
| `/api/v1/checkout/sessions/{id}/clarify` | POST | 用户确认 / 修正歧义商品 |
| `/api/v1/checkout/sessions/{id}/confirm` | POST | 锁定账单（促销 + 会员价计算） |
| `/api/v1/orders/{id}/pay` | POST | 发起支付，回调更新状态 |

### 4.4 关键数据模型

| 表 | 关键字段 |
|---|---|
| `product` / `sku` | sku_id、名称、规格、条码、价格、营养成分、过敏原 |
| `sku_visual` | sku_id、样本图、特征向量、包装版本、生效状态 |
| `shelf_location` | sku_id、货架、层号、坐标（支撑"在哪儿"问答） |
| `checkout_session` | 会话、设备、用户、状态机状态、总重、图像留痕地址 |
| `checkout_item` | sku_id、数量、**置信度**、判定来源（视觉/重量/人工）、快照 |
| `review_ticket` | 会话、可疑项、复核结果、回流用于模型迭代 |
| `order` / `payment` | 订单、优惠明细、支付流水、对账状态 |

### 4.5 结账状态机

```
CREATED → CAPTURING → RECOGNIZING → NEED_CLARIFY → CONFIRMED → PAYING → PAID → CLOSED
                                  └→ REVIEWING ┘
任意阶段异常 → FAILED
```

## 五、关键技术难点与对策

| 难点 | 风险 | 对策 |
|---|---|---|
| 相似包装误判（同品牌不同口味） | 算错钱，引发投诉 | 检测 → 特征检索 → Top-K 差异放大 → 卡阈值转人工；绝不硬出账 |
| 堆叠遮挡漏检 | 直接损耗 | 双相机 + 实例分割 + 主动引导"请摊开商品" + 称重偏差校验 |
| 新品 / 换包装冷启动 | 识别率骤降 | 入库转台自动拍多视角建档；换包装触发重采样与回归测试 |
| 端到端延迟 | 排队，体验崩 | 边缘 TensorRT 推理 + 检测/特征并行 + 热门 SKU 特征常驻显存 |
| LLM 幻觉（营养 / 过敏） | 法律风险 | 工具调用替代自由生成；答案强制带引用；敏感问题走白名单库 + 免责提示 |
| 争议与隐私合规 | 监管风险 | 全链路留痕；视频边缘处理、人脸脱敏、明示告知与留存期限 |

## 六、实施路线

| 阶段 | 目标 | 产出 |
|---|---|---|
| M1 | 商品主数据 + 导购问答 | SKU 库、RAG 问答可用 |
| M2 | 视觉识别 MVP | 单品 / 少量品识别 + 复核工单 |
| M3 | 结账闭环 | 账单 + 支付 + 留痕 |
| M4 | 精度与防损 | 重量校验、相似品攻坚、损耗报表 |
| M5 | 规模化 | 多店复制、离线降级、模型自迭代 |

## 七、待确认事项

1. 目标门店规模与 SKU 池体量（决定选型：pgvector 还是 Milvus）
2. 是否必须支持刷脸支付（涉及更高合规要求）
3. 是否需要私有化部署大模型（成本与延迟权衡）
4. 是否已有硬件清单（相机型号、是否带称重、边缘盒子算力）
5. 结算准确率的可接受门槛与损耗责任归属
