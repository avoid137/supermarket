# 导购 Agent 评测集与三方案消融

这个目录回答一个问题：**改了 prompt、改了检索、加了约束之后，系统到底变好还是变坏了？**

在此之前，仓库里只有 `tests/` 下的断言式测试——它们能回答「这次改动有没有弄坏已有功能」（回归），
但回答不了「导购答得准不准、有没有在编」（效果）。两者是互补的，不能互相替代。

---

## 一、三种配置（消融实验）

同一套 66 条用例，跑三种配置。A→B 只加了工具，B→C 只加了约束：

| 代号 | 名称 | 注册工具 | system prompt | 衡量的东西 |
|---|---|---|---|---|
| **A** `pure` | 纯 LLM 直答 | ❌ 不注册 | 只给店员人格，不给任何规则 | 没有店内数据接入时，模型会编多离谱 |
| **B** `tools` | 仅工具调用（无约束） | ✅ 7 个（6 领域 + 1 兜底 SQL） | 只给店员人格，不给任何规则 | 光把工具挂上去够不够 |
| **C** `guard` | 工具 + 边界约束（**线上现状**） | ✅ 7 个（6 领域 + 1 兜底 SQL） | `app/prompts/guide.yaml` 完整提示词 + 第二轮硬约束 | 「给大模型划边界」的增量收益 |

> 说明：原来的方案写的是「纯 LLM 直答 vs 仅工具调用 vs 检索+工具」。在本项目的架构里
> **工具本身就是检索层**（`search_product` 内部走混合检索），不存在「有检索但没工具」的第三态，
> 所以第三组改定义为「工具 + 边界约束」——它才是线上真实跑的那一版，也是本项目方法论
> （闭卷选择 / 禁止凭记忆作答 / 允许说不知道）的落点。这样 B→C 的差值就直接量化了「约束」的价值。

C 组的第二轮与线上完全一致：回灌工具结果后追加 `no_more_tool_calls_note()` 硬约束，
且第二轮**不传 tools 参数**——从协议层面就调不了工具，而不是靠提示词求它别调。

## 二、用例构成（66 条）

| 类别 | 条数 | 说明 |
|---|---|---|
| 营养成分 | 10 | 含配料表原文、酒精度这类「不在营养表里的数」 |
| 价格 | 8 | 含同款不同规格（乐事 70g/40g）、品牌下多商品（农夫山泉 水/果汁） |
| 货架位置 | 6 | 含口语化问法（在哪儿 / 怎么走） |
| 过敏原 | 6 | 含排除型需求（「没有花生和坚果的零食」）与规格间过敏原差异 |
| 库存 | 5 | 三态口径 + 购买决策（买 10 瓶够吗） |
| 促销 | 4 | 含「同品牌有促销、另一款没有」的边界 |
| 语义检索 | 4 | 字面零重叠的属性描述（红色罐装饮料 / 大瓶装日用品） |
| 负例·拒答 | 4 | iPhone / 隔壁超市价格 / 三文鱼刺身 / 止痛药 |
| 搭配推荐 | 3 | 开放推荐 |
| 多条件筛选 | 3 | 聚合（最便宜）/计数（几款零食，均属「算整张表」）/交集（无糖且是茶）；G47、G48 |
| 聚合计算 | 8 | MIN（最便宜）/MAX（最贵）/计数（某类共几款）/排名第（第 2 贵）/价格排序 Top-3/跨商品比价；G59–G66，真值均由 snapshot 派生 |
| 多轮对话 | 3 | 指代消解（「那还有货吗」「它含糖吗」）+ 跨轮换意图 |
| 开放咨询 | 2 | 提神好物 / 送人礼盒 |

其中 **3 条多轮**、**3 条应拒答**、**5 条开放性提问**（不参与越界判定）。

### 真值不手抄

所有价格 / 货架 / 库存 / 营养 / 过敏原的期望值都从 `catalog_snapshot.json` 取，
而该快照由 `app/data/products.py` 派生。用例里写的是 `{"t": "price", "sku": "SKU009"}`，
具体数字在打分时才解析——**避免人肉誊写数字引入的错误**，也让改商品数据后不必改用例。

## 三、指标定义

完整判据写在 `score_eval.py` 文件头。要点：

- **事实正确率**：该题的事实全部被回答覆盖。
- **幻觉率**：回答里出现数据库不支持的**具体店内断言**。四类硬判据——命中 forbid、
  凭空价格（不等于库内任何售价/会员价）、凭空货架（不是 A1/A2/A3）、应拒答却给断言。
  差额语境（省 X 元）与数量派生语境（第二件半价 → 两瓶 X 元）**不算**凭空报价。
- **库外商品率**：推荐了库内没有的商品（如「无糖就喝绿茶」「可以买饭团」）。
  这类错误没有可校验的数值，只能靠词表启发式，所以**单独统计、不并入幻觉率**。
- **越界率**：提到了本题范围外的在库商品名。开放性提问不参与判定。
- **工具命中率**：实际工具调用满足用例期望。`pure` 组不注册工具，指标为空。

### 判据经人工复核

自动化判据的第一版有 3 类误报，全部在人工逐条读证据后修正（见 `score_eval.py` 里的注释）：
品牌连带匹配（说「乐事」被判成提到了 4 个乐事 SKU）、把正确的算术总价当成凭空报价、
把「避开：士力架」这种正确提醒当成误荐。

## 四、怎么跑

```bash
cd backend

# 1) 准备：密钥（backend/.env 里的 LLM_API_KEY）+ 把数据库重置回种子态
python -m app.db.seed --force

# 2) 出题：从商品主数据重建快照（重置过数据库或改了 products.py 才需要）
python eval/refresh_snapshot.py

# 3) 跑三组（约 2 分钟，198 次调用）
python eval/run_eval.py --arm all

# 4) 打分（不调模型，改判据可零成本重跑）
python eval/score_eval.py
```

产物：

```
eval/
├── cases.json                 66 条标注用例
├── catalog_snapshot.json      本次评测所依据的商品主数据快照（真值来源）
├── run_eval.py                执行器：只跑不判，落盘 raw_*.jsonl
├── score_eval.py              打分器：只读不跑，产出指标与明细
├── refresh_snapshot.py        重建商品快照
└── results/
    ├── raw_{pure,tools,guard}.jsonl   逐题原始记录（含工具调用轨迹与 token 用量）
    ├── metrics.json                   机器可读指标
    ├── report.md                      人读报告：总表 + 分类别 + 全部问题用例明细
    └── prefix/                        修 bug 之前的原始记录，用于前后对比
```

`run` 与 `score` 分离是刻意的：**判据一定会改**，分离后改判据不用重新烧 API 额度。

## 五、检索层对照实验（`retrieval_ablation.py`）

三方案消融回答的是「工具和约束有没有用」；这个脚本回答的是「检索本身该怎么实现」。

线上 `search_product` 走的是 `hybrid_score`：字面分 × 0.35 + 词典式属性语义分 × 0.65。
这个配比一直是设计出来的，没人验证过换别的做法会怎样。这里补上。

同一套用例、同一份商品库，只换排序逻辑跑 9 种策略，并且**跑两个输入口径**：

| 口径 | 输入 | 模拟什么 |
| --- | --- | --- |
| `raw` | 顾客原话 | 上游没有做任何查询改写 |
| `llm_kw` | LLM 改写出的关键词 | 线上真实链路（模型调 `search_product` 时传的是短词） |

口径二（贴近线上）的结果：

| 策略 | Recall@1 | Recall@3 | MRR | 库外题返回空 |
| --- | --- | --- | --- | --- |
| 纯字面（关键词） | 84.6% | 84.6% | 0.846 | 100% |
| 纯属性语义（规则词典） | 44.2% | 53.8% | 0.488 | 100% |
| **现线上**（两路加权求和） | 92.3% | 94.2% | 0.931 | 100% |
| 两路 RRF（字面 + 属性，无向量） | 82.7% | 92.3% | 0.877 | 100% |
| 三路加权求和（+ 向量） | 92.3% | 96.2% | 0.942 | 100% |
| 纯向量（text-embedding-v3） | 94.2% | 98.1% | 0.956 | **0%** |
| 三路 RRF（向量也参与放行） | 96.2% | 96.2% | 0.964 | **0%** |
| **三路 RRF + 结构化闸门** | **96.2%** | **96.2%** | **0.962** | **100%** |

### 结论一：口径选错会得出相反的建议

raw 下纯向量 92.3% 对现线上 84.6%，看起来「该换向量了」；但 `llm_kw` 下差距只有 **+1.9pp**——
向量的强项是扛住长口语问句（「抽纸在哪个区？」），而线上模型传进来的本来就是「抽纸」这种短词，
这项优势被上游的查询改写提前吃掉了。佐证：字面策略受改写影响最大（+9.6pp）、向量最小（+1.9pp），
两者是同一件事的两面。

### 结论二：「向量路」与「RRF 融合」必须配套（这条是被自己推翻后修正的）

|  | 两路（字面 + 属性） | 三路（+ 向量） |
| --- | --- | --- |
| **加权求和** | 92.3%（现线上） | 92.3% |
| **RRF** | 82.7% | **96.2%** |

- 加权求和下加向量路：**没有任何变化**。等权归一化平均把向量的区分度稀释掉了
  （余弦 top1 归一化后 1.0、第二名 0.98）。
- RRF 下加向量路：**+13.5pp**。向量单路 R@1 94.2% 是全场最高的排序质量，而 RRF 靠排名投票、
  不靠分数求和，正好能用上它：向量认为对的商品，即使字面 / 属性路只排第 3~5 位，
  三路名次叠加后也能顶到第一。
- RRF 在两路时反而比加权求和差 **9.6pp**。

> ⚠️ 这个结论**修正过一次**：第一轮只对比了「两路加权 vs 三路 RRF」，就直接得出
> 「该换的是融合方式」。补测两路 RRF 与三路加权这两个格子后才看清是**交互效应**——
> 单加向量无效、单换融合有害，两者配套才有 96.2%。**这是本次实验最值得讲的一处：
> 结论被自己的下一组数据推翻，然后修正。**

### 结论三：向量不能兼任「库里有没有」的闸门

纯向量召回最高，却一条库外题都挡不住（「iPhone」→ 卫龙亲嘴烧、奥利奥、蒙牛雪糕）。
扫阈值可见：库外题最高余弦 0.530、库内题最低 0.475，两条分布重叠；要把库外题全挡住得把阈值
提到 0.60，那时库内题只剩 40/52 能过。**余弦里根本不包含「库里有 / 没有这件东西」这个信息**，
闸门只能交给结构化信号（字面命中 / 属性命中）。

**还有一条负结果**：`三路 RRF + 结构化闸门 + 强向量补召回` 与不带强向量版的全部指标完全相同——
0.60 那条补召回路径没有任何增量，属于应该删掉的复杂度。留在报告里，免得下次再想一遍。

### 结论四：检索层指标 ≠ 端到端收益（这条决定了「要不要改线上」）

检索层 92.3% → 96.2% 看起来漂亮，但**它不会自动转化成端到端收益**：

- C 组（线上现状）端到端 98.3%（Sep-16 baseline，当时 58 条；扩到 66 条后受 temp 0.3 方差影响在 93–98% 波动，见第七节），
  12 个类别里 11 个满分，**唯一失分是 G47**
  （「饮料里最便宜的是哪个？」）——根因是模型**没调用 SQL 兜底做 MIN 聚合**，
  属工具选择问题，不是检索召回问题（**已在 P1-2 修复、且 P0 聚合类扩到 10 条验证泛化，见第七节、第八节**）。
- **66 条里与检索召回相关的失分：0 条。**

原因不难理解：检索层之上还有一层 LLM，它拿到工具结果后会再做一轮筛选、解释与兜底，
检索层的少量排序误差被消化掉了。所以：

> **离线组件指标（R@1 涨 3.9pp）≠ 产品指标（端到端涨 0）。**
> 做改动决策时必须看后者的**分类别拆解**，否则很容易为了一个漂亮的分项数字去动主链路。

这条还顺带暴露了一个相反方向的信号：**B 组（无约束）在多条件筛选上 100%，C 组（有边界约束）
只有 67%**——约束让模型更保守，反而不去主动调兜底工具。3 条样本不足以下结论，仅作记录。

```bash
cd backend
python eval/retrieval_ablation.py               # 两个口径都跑
python eval/retrieval_ablation.py --mode raw    # 只跑原句口径
python eval/retrieval_ablation.py --re-embed    # 向量缓存作废重算
```

向量用 DashScope `text-embedding-v3`（1024 维，与项目其他调用同一个 Key），
按文本缓存到 `retrieval_vectors.json`；查询改写缓存在 `retrieval_queries.json`（58 条，可人工复核）。
**没有引入 FAISS**：29 个向量做穷举点积是微秒级，为这个规模装向量索引属于过度设计。

## 六、已知局限

- **66 条是够发现问题、不够下结论的规模。** 单条差异 1 条 ≈ 1.5 个百分点，
  所以只报趋势，不把 2~3 个百分点的差距当结论。
- **库外商品率是词表启发式**，词表在 `score_eval.py` 里可见可改，会有漏报。
- **幻觉率是下限**：只有能被自动校验的断言（价格 / 货架 / 库存 / 库外商品）才计入，
  「把 A 商品的配料说成 B 的」这类语义错误只能人工发现。
- **温度为 0.3**（线上作答那步实际是 0.4），是为降低多次运行之间的方差，刻意偏离线上。
- **用例由作者本人编写**，存在「按自己系统的能力设计题目」的偏差。真值虽由数据库派生，
  但**考什么**是主观的——这也是为什么它只能算内部评测，不能算基准。
- **检索实验里的强向量阈值 0.60 是在同一套评测题上扫出来的**，严格说存在过拟合；
  换数据后应重新扫，或者改用「与第二名余弦的差值」这类相对判据。
- **检索实验 52 条样本，单条 = 1.9pp**，与三方案消融是同样的规模问题：只报趋势不报结论。
  另外 `llm_kw` 口径依赖一次性 LLM 改写（已缓存可人工复核），**改写质量本身没有被评测**——
  如果改写把关键词写歪了，实验会把这笔账算到检索策略头上。

## 七、P1-2：工具选择修复（聚合题误走 search_product）

第六节结论四挖出的真短板：**G47「饮料里最便宜的是哪个？」在线上组用 `search_product` 答错**
（把可口可乐当成最便宜的饮料），根因是工具选择而非检索召回。本节点清理并修复它。

### 量化（工具选择问题的真实规模）

66 条用例里，需要「算整张表」的聚合 / 比较 / 排序类：原 baseline 仅 **2 条**（G47/G48），**P0 已扩到 10 条**（G47/G48 + G59–G66，见第八节）：

| 用例 | 类型 | 原 baseline（guard）工具 | 结果 |
| --- | --- | --- | --- |
| G47 | MIN（最便宜） | `search_product` | ❌ 答错（返回相关度前几，不是最便宜） |
| G48 | COUNT（共多少款） | `query_product_database` | ✅ 已正确走 SQL |

**原 baseline 真正因工具选择答错的只有 G47 这 1 条**（G48 这类 COUNT 本来就会走 SQL）。
工具命中率 0.9815 → 修复后 **1.0**。根因定位：guard 提示词旧 rule #6
「`query_product_database` 是兜底工具，预设能答就别写 SQL」让模型对极值 / 排序类题
误以为 `search_product` 能答——而 `search_product` 一次只返回按相关度排序的前几件，
**根本做不了 MIN / 排序 / 聚合**，硬凑必然答错。

### 修复

改写 `backend/app/prompts/guide.yaml` 两处：

1. **rule #6** 从「SQL 是兜底、预设能答就别写」改为「工具选型原则」：
   - 单一商品属性（多少钱 / 在哪 / 含什么过敏原 / 有无货）→ 预设工具；
   - **要算整张表（最便宜 / 最贵 / 价格排序 / 共多少款 / 均价 / 排名第 / 跨商品比价）必须直接写 SQL 走 `query_product_database`**，
     并点明「`search_product` 做不了排序和聚合，硬凑会答错（如把可口可乐当最便宜）」；
   - `query_product_database` 仍是只读兜底，简单查询不要写 SQL。
2. **`query_product_database` 工具描述**：从「仅当预设都答不了才用」改为
   「用于预设工具做不到的计算型问题：最便宜/最贵、按价格排序、共多少款、均价、排名第、跨商品比价」，
   并提示 search_product 无法排序聚合。

### 验证（必须诚实标注方差）

修复后 G47 **稳定走 `query_product_database` 并答对**（农夫山泉 ¥2.0）——方向正确，
消除了「聚合题误走 search_product」这一系统性错误路径。

但 DeepSeek 在 **temp 0.3 下非确定性**，单条重跑的前后对比会**被方差淹没**，不能据此下结论。
同日「旧提示词 vs 新提示词」双版本对照显示单题**随机翻面**（G37 新版反而更好；
G32/G36/G39 新版变差、G35/G38 两版都差），端到端事实正确率在 **93–98%** 间波动
（Sep-16 baseline 98.3%，同日两次重跑 93.1%）。**G47 在旧版同日重跑里也碰巧走了 SQL 答对**，
进一步说明它受方差影响。

> 结论：**修复行为正确（移除聚合题的错误工具路径）。** 原 baseline 仅 58 条、聚合类只有 1 条（G47），
> 小样本无法统计证明净准确率增益；**P0 已将聚合类扩到 10 条（G59–G66 覆盖 MIN/MAX/COUNT/排名第/排序 Top-3/跨商品比价），
> guard 组 10/10 事实正确 + 10/10 工具命中，修复泛化到全部聚合类型得到验证（见第八节）**——
> 与「小规模只报趋势不报结论」的既定口径一致，但泛化结论已从「单题可复现」升级为「10 题全类覆盖」。
> 修复仍保留：它没引入任何可追溯的回归（翻面是双向随机的，不是新版单边变差），

### 教训（验证 LLM 改动的方法论）

- **不要用「一次重跑的前后对比」验证 LLM 改动**：temp > 0 时单题方差会淹没真实效应。
  要做**同日、同输入、双版本（旧/新）对照**，且样本量要足以分离效应。
- 这呼应 P1-1 的精神：**看产品指标的分类别拆解，并承认小样本局限**；
  组件/单题指标变好 ≠ 端到端净增益，没把握时就如实标注「方向正确、待大样本确认」。
  - 对照用的原始记录归档在 `eval/results/baseline_pre_p1_2/`
  （`raw_guard_NEWprompt.jsonl` / `raw_guard_OLDprompt_sameday.jsonl` / 原始 Sep-16 `raw_*.jsonl`）。
